# Postbox security review — 28 October 2026

**Remediation status:** The findings below describe the original reviewed snapshot. All four have since been addressed in source; see [remediation details and verification](remediation-2026-10-28.md). The original evidence is retained for traceability.

This is a first-party review of Postbox 0.1.0 against its design, not an independent audit or a guarantee that all vulnerabilities have been found. Four actionable findings were identified. Fix the two inbound-processing dependencies first, then the browser review/send race and bucket ownership validation before an OSS production release.

Production was inspected read-only. No email was sent, DNS/policies changed, resources deleted, or fixes deployed. Reproductions used synthetic mail in isolated workerd/D1/R2 instances and a fake cf executable. Application source and dependency versions were left unchanged. [Evidence and source hashes](review-evidence-2026-10-28.json) identify the reviewed files and outcomes without credentials or real mail.

## Findings

### R1 — High / P1: vulnerable MIME parser on unauthenticated email ingress

**Code:** `package.json:23`, `src/server/mail.ts:378`.

The application pins `postal-mime` 4.0.5. The maintainer identifies versions before 4.0.8 as affected by quadratic decoding of repeated encoded header words. Incoming mail reaches this code without a mailbox Access session; the attack requires a configured recipient, not a login. A lower header budget reduces the cost of one parser instance but does not fix this version's separate budgets for inline RFC822 messages. [Maintainer advisory and patched version](https://github.com/postalsys/postal-mime/security/advisories/GHSA-f2hq-32vh-53cc).

**Evidence:** Using the application's exact parser options, a 384,407-byte multipart message with two inline RFC822 messages and 384,000 combined subject-header bytes parsed successfully despite `maxHeadersSize: 262144`. Single-header samples up to 256,079 message bytes also parsed. This demonstrates that the intended header budget is not global. Local timing was modest (58 ms for the nested example); this review does not claim to have exhausted a production Worker or reproduced a global outage. The upstream complexity defect and independently renewed sub-message budgets make leaving the parser unpatched unsafe.

**Impact:** A sender can impose excess processing cost and stress intake/queue capacity. This is an availability/cost issue, not a demonstrated confidentiality breach. Keeping web, intake and sending in one Worker leaves them sharing an application resource boundary.

**Fix:** Upgrade to a tested release containing the 4.0.8 fixes or later. Keep explicit byte/part/depth limits and add aggregate nested-header/part regression cases. Validate maximum-size MIME behavior in workerd. Do not treat the existing header limit as a substitute for updating.

### R2 — Medium / P2: small HTML payload reliably poisons intake

**Code:** `package.json:26`, `src/server/security.ts:87`, `src/server/mail.ts:418`.

The pinned `sanitize-html` 2.18.0 recursively re-sanitizes the fallback of discarded iframes. The application's allowlist excludes iframes and uses the affected default discard behavior. The 1,000,000-character HTML preview limit does not prevent this failure. [Maintainer advisory; fixed in 2.18.1](https://github.com/apostrophecms/apostrophe/security/advisories/GHSA-c9rx-x947-fp3h).

**Evidence:** The actual application `safeHtml` function threw `RangeError` with an 8,000-byte input. Through the real workerd intake path, a 16,131-byte synthetic HTML email failed on all three processing attempts and became `failed` intake. This fits comfortably below the 25 MiB SMTP limit and HTML preview bound.

**Impact:** An unauthenticated sender can make their messages fail ingestion and consume repeated queue work. The raw original survives and retries are bounded, which limits impact; no script execution or mailbox takeover was demonstrated.

**Fix:** Upgrade to 2.18.1 or a later tested patched release. Add this case to parser/sanitizer regressions and consider a bounded plaintext fallback when only HTML rendering fails, preserving the original. A nesting option alone is not a reliable workaround for the affected version.

### R3 — Medium / P2: browser sends can bypass the reviewed-draft revision check

**Code:** `src/client/main.tsx:1279`, `src/server/api.ts:351`, `src/server/mail.ts:100`.

The CLI submits a reviewed revision, but the browser sends `{}` after saving. The API makes `revision` optional, so a concurrent editor can change recipients/body between the browser's completed save and submission. The server then snapshots and queues the new contents. Its SQL revision guard protects changes during submission, but cannot identify an earlier revision that the human reviewed.

**Evidence:** In isolated workerd, create revision 1 addressed to `reviewed@example.test`; update it to revision 2 addressed to `changed@example.test`; submit with revision 1 and receive 409. Submit with the browser's `{}` instead and receive `queued`; the immutable outbox payload contains `changed@example.test`.

**Impact:** In a shared-admin mailbox or concurrent agent/browser editing workflow, the human can send contents or recipients they did not review. This is not an unauthenticated escalation: another permitted editor is required, or a legitimate concurrent edit must occur. It undermines the intended review-and-send boundary.

**Fix:** Require the expected revision for new send submissions and submit the revision returned by the browser's save. Preserve idempotent handling of an already queued submission. Add an interleaved browser-save/second-editor/send regression; reject missing revisions rather than silently accepting the latest contents.

### R4 — Medium / P2: same-name replacement R2 buckets pass destructive ownership checks

**Code:** `scripts/mailbox.mjs:112`, `scripts/mailbox.mjs:422`, `scripts/mailbox.mjs:431`, `scripts/mailbox.mjs:459`.

The installer records an R2 bucket's name as both its name and ID and discards creation metadata. Cleanup obtains that name and checks the name again. If the original bucket is deleted outside Postbox and another bucket is created under the same name, the old installation manifest still authorizes draining and deleting it. Prefix confirmation does not distinguish the two bucket incarnations.

**Evidence:** A fake-provider installation returned a bucket with the expected name but a replacement creation date during deletion preflight. Uninstall accepted it and called bucket deletion. The production deletion path lists and bulk-deletes bucket objects before deleting the bucket. No real bucket or object was deleted during this review.

**Impact:** An operator cleaning up an old installation can delete unrelated data in a recreated bucket, violating the design's owned-resources-only cleanup requirement. This requires prior external lifecycle changes and an explicitly authorized destructive command; it is not an Internet attack.

**Fix:** Record and verify provider creation metadata and an installation-specific ownership marker before object deletion. Fail closed when identity metadata is missing or mismatched, including older manifests, unless an operator explicitly reconciles ownership. Recheck before draining and test a same-name/different-creation-time bucket.

## Dependency assessment

The current full `npm audit` reports 11 affected dependency entries: 7 high, 3 moderate, 1 low, 0 critical. Production-only audit reports 3 entries: `postal-mime` high, `sanitize-html` moderate, and its `deepmerge` dependency low. Counts include transitive propagation and do not mean 11 independently exploitable application issues.

The `deepmerge` issue involves merging attacker-controlled object keys; the reviewed application supplies constant sanitizer options, so this review did not establish a reachable prototype-poisoning path. Keep it in the sanitizer update rather than presenting it as a proven mailbox exploit.

The remaining alerts involve the cf/Vite/Miniflare toolchain and nested Zod/Undici dependencies. They are not evidence of seven separate deployed Worker vulnerabilities. Update the beta toolchain as a tested group. Avoid a blind `npm audit fix --force`: the suggested Miniflare resolution includes a major downgrade. The CI audit gate would currently fail on high-severity advisories even though functional tests pass.

## Controls checked successfully

- The code verifies Access signatures, issuer, audience, expiry and exact human emails, rejects service identities, and checks the canonical origin before UI/API/files.
- Current live Access configuration has one policy, the expected exact-email allowlist, the required IdP and account-membership condition, and the configured hostname.
- Current R2 managed public access is disabled and the bucket has no custom domains. These were read through cf; no objects were downloaded.
- Anonymous requests carrying forged assertion/email headers to the UI, bootstrap, export and an attachment path all received Access login redirects. This verifies the tested public paths, not every possible deployment setting.
- CSRF origin/custom-header checks, bound SQL, UUID validation and per-draft attachment checks are present. Addresses share a trusted workspace by design; absence of per-user row isolation is not a defect in that design.
- Email rendering has a restrictive sanitizer allowlist, an opaque sandboxed iframe, CSP, blocked remote images and forced downloads for active file types. No stored-XSS path was found in the reviewed code/tests.
- Sends use immutable snapshots, atomic claims and conservative `unknown` handling for ambiguous provider outcomes. CLI sending requires explicit confirmation and sends a revision.
- CLI session files use mode 0600, mail requests do not follow redirects, and loopback mode does not forward Access tokens.
- Cleanup checks account/prefix/recorded resource IDs, retains shared policies when referenced, and removes the serving Worker before Access. R4 is a specific gap in the bucket identity model.
- The existing 66 tests and workerd/D1/R2 integration suite pass. Passing these checks does not cover the new findings; the additional isolated reproductions expose the gaps.

## Design hardening and remaining limits

These are recommendations or accepted tradeoffs, not additional confirmed vulnerabilities:

- Keep MFA optional by design. Its disabled default is intentional and is not counted as a finding.
- Agent sessions currently have the allowed human's full mailbox permissions. CLI confirmation and help text are workflow controls, not a server-enforced draft-only permission. Optional scoped read/draft credentials would reduce prompt-injection impact for agents meant only to prepare mail.
- Add per-address and installation-wide intake/storage budgets and notifications. The current 25 MiB limit bounds each mail, not aggregate storage or a mail flood. Never rely on Access to protect the SMTP entry point.
- Add durable, privacy-conscious audit events for draft submission, send/undo, and relevant administrative operations. Current audit calls cover only a subset of mutations.
- Extend `doctor` to detect public R2 exposure and missing account-membership/IdP restrictions after configuration drift. Correct live settings were verified in this review, but `doctor` does not fully assert all of them.
- `SafeMessage` fetches any referenced CID attachment before creating a blob; restrict fetching to intended raster inline images to match the architecture claim and reduce client memory use.
- Separate web/intake/sending Workers if stronger runtime isolation becomes a priority. Current consolidation is an explicit lightweight-design tradeoff.
- Authenticated remote CLI operations, independent authorized/unauthorized human login attempts, maximum-size MIME memory exhaustion, full browser fuzzing, provider delivery-event authenticity in live use, and destructive live teardown were not exercised here. No penetration-test or compliance certification is implied.

Recommended order: patch R1/R2 and rerun intake/security tests; close R3 with browser/server concurrency tests; close R4 with replacement-bucket cleanup tests; then update toolchain dependencies and improve drift/abuse monitoring. The findings above were unfixed at review time; the linked remediation record tracks the subsequent fixes.
